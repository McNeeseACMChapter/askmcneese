HOW TO USE THIS INDEX

The repository contains current guides, implementation records, architecture proposals, design artifacts, historical audits, screenshots, and backlog documents. They are not all descriptions of the same revision. For runtime truth use this precedence:

1. Current executable code and loaded configuration.
2. Current tests and data manifests.
3. Feature-specific implementation records that match the code.
4. Architecture and design documents.
5. Historical reports, screenshots, plans, and backlog material.

If a document conflicts with current code, record the conflict. Do not silently implement the document as if it were already approved runtime behavior.

DOCUMENTATION DEBT

- Current-state and target-state descriptions are mixed.
- Completion language is sometimes stronger than behavioral evidence.
- Port, feature-flag, and provider assumptions can become stale.
- Multiple implementation records are modified alongside code and may describe an uncommitted state.
- No single generated capability/coverage report ties source groups to indexed chunks, freshness, route tests, and answer-quality results.

RECOMMENDED DOCUMENTATION POLICY

Every architecture or capability document should declare:

- status: current, target, historical, or experimental
- code revision
- data/index revision
- configuration profile
- verification date
- evidence used
- owner
- known limitations

Generate runtime inventories where possible. Keep human-authored documents for intent, decisions, risks, and interpretation.
