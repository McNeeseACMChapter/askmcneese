==================================================

DECISION ID: D-01
TITLE: Backend/crawler code-sharing strategy

STATUS: RECOMMENDED — PRINCE APPROVAL REQUIRED

CURRENT REALITY:
Backend and crawler are independent Python roots. Real duplication exists but each side has
diverged intentionally. There is genuine, non-trivial duplication of HTML→Markdown conversion,
USER_AGENT strings, Cloudflare markers, registry CSV loading, and stopword sets.

EVIDENCE:
- file: backend/app/services/web_search.py
  symbol/section: USER_AGENT (L36), CLOUDFLARE_MARKERS (L58), _table_to_markdown/_list_to_markdown
    (L105-148), _extract_structured_content (L181)
  behavior: body-first structure-preserving extraction tuned for live pages; truncates at 10k.
- file: crawler/clean_text.py
  symbol/section: _table_to_markdown (L39), _HEADINGS/_STRIP_TAGS (L22-24), sentinel block markers
  behavior: strip-tags-first extraction with heading markers and sentinel wrappers for chunking.
  → The two HTML→Markdown implementations differ in inputs and goals (ingest cleaning vs. live
    fetch filtering). PHASE 5/O-05 flags this duplication as HIGH migration risk.
- file: backend/app/services/source_registry.py  symbol: load_registry (L114), RegistrySource
- file: crawler/source_registry.py  symbol: load_registry (L48), Source (with approval_status,
    trust_tier, crawl_scope)
  behavior: BOTH read knowledge/source_registry_seed.csv with utf-8-sig, but expose DIFFERENT
    dataclasses for different purposes (backend routing keywords vs. crawler approval gating).
- file: crawler/config.py  behavior: crawler is flat-module (no __init__.py) — a shared package
    would force import-path changes across crawler + backend.

OPTIONS:

OPTION A:
Description: Keep backend and crawler fully independent; accept duplication.
Benefits: No packaging migration; backend deploys without crawler; simplest import paths; matches
  current flat-crawler design.
Risks: Duplication drift (the HTML→MD logic can diverge silently).
Files affected later: none (status quo).

OPTION B:
Description: Introduce a lightweight top-level common/ package for the truly shared, dependency-light
  helpers (html_markdown, http/USER_AGENT+Cloudflare, registry schema loader, stopwords).
Benefits: Single source of truth; removes O-05/O-06/O-19 duplication.
Risks: Forces crawler packaging (D-13) and backend import-path changes; the two HTML→MD variants are
  NOT drop-in equal, so consolidation without fixtures would change extraction output.
Files affected later: new common/html_markdown.py, common/http.py, common/registry.py; consumers in
  backend/app/services/{web_search,source_registry}.py and crawler/{clean_text,source_registry}.py.

OPTION C:
Description: Keep code independent but add cross-implementation CONTRACT TESTS (fixture-based) that
  assert the two HTML→MD paths produce equivalent structured output on shared samples, before any
  future consolidation.
Benefits: De-risks a later common/ move; catches drift now; no packaging change.
Risks: Adds test maintenance; does not remove duplication yet.
Files affected later: backend/tests/ (fixtures + comparison tests) only.

RECOMMENDATION: Option C now, Option B later (after fixtures + D-13 packaging decision).

WHY: The duplication is real but the two HTML→Markdown paths are behaviorally different and tuned
for different inputs; consolidating them blindly would change answer content. A contract-test harness
is the safe precondition. A common/ package should not be created until crawler packaging (D-13) and
deployment independence are settled.

SPRINT 3 WORK BLOCKED UNTIL DECISION: NO (contract tests can start now; consolidation is later)
BLOCKED TASKS: common/ package creation; HTML→MD consolidation; shared USER_AGENT/registry loader.

- file: .gitignore  section: knowledge/ is NOT ignored (only knowledge/cache/) → any committed CSV
    ships in git; merged/sitemap/catalog/pdf CSVs are currently untracked (see D-11).

Determinations:
- Pending_Review rows CAN currently be ingested when ALLOW_PENDING_SOURCES/ include-pending is set.
- Approval gating lives in the crawler (crawl_allowed + pm_approved), not the backend.
- Backend web routing intentionally uses curated seed data ONLY.
- Merged data can go stale (it is a generated snapshot).

OPTIONS:

OPTION A — DUAL RESPONSIBILITY (MODEL A):
Description: seed = approval + routing authority; merged = ingestion execution manifest.
Benefits: Matches current code exactly; curated routing stays small/trusted; ingestion can scale wider.
Risks: Two files to keep coherent; merged staleness.
Files affected later: documentation of the contract; possibly a "generated-from" header in merged.

OPTION B — SINGLE MERGED AUTHORITY:
Description: merged drives both routing and ingestion.
Benefits: One file.
Risks: Backend routing would inherit 400+ unvetted rows; approval gating semantics blur; larger
  keyword matching surface. Requires backend routing rewrite.
Files affected later: backend/app/services/source_registry.py (routing), crawler consumers.

OPTION C — CANONICAL DB/SCHEMA LATER:
Description: CSVs become generated views of a structured registry (DB/schema).
Benefits: Strong provenance/auditing.
Risks: Over-engineered for current stage.
Files affected later: new registry store + generators.

RECOMMENDATION: Option A (dual responsibility) for Sprint 3; keep backend routing on seed only.

WHY: The code already implements Model A cleanly, and it preserves a small, human-approved routing
authority while allowing wider ingestion. Switching to merged-as-routing (B) would expose unvetted
rows to answer routing. This is a data-contract decision Prince should ratify.
