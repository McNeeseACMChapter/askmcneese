STRUCTURAL WEAKNESSES AND FAILURE MODES

SEVERITY 0 — FUNDAMENTAL PRODUCT TRUTH

1. The system cannot tackle every problem.

It has no authenticated student-system connectors, no universal campus ontology with verified data for every entity, no reliable external-network guarantee, and no broad semantic evaluation demonstrating unseen-query performance.

2. Declared capability is much broader than content-bearing evidence.

There are 44 source groups, but only 19 currently have positive indexed chunks. Twenty-five source groups have zero chunks. Many “live_official” domains therefore depend on a successful live request or a destination-only registry record.

3. Classification correctness is not independently verified.

Evidence sufficiency validates the compiler’s chosen schema. A wrong schema can accept irrelevant evidence. This is the most important backend design gap.

SEVERITY 1 — OBSERVED CORRECTNESS FAILURES

4. Cross-domain compound questions can route to the wrong pack.

Observed international-registration question routed to student_services and bookstore/housing/dining sources. It was still marked CAN_RELEASE and success.

5. Conversation task state can contaminate unrelated turns.

Observed unrelated language remained attached to an academic-calendar task and produced a clarification response.

6. “Success” does not mean correct.

Current statistics count final_status=success. Clarifications, zero-result responses, deterministic destinations, and semantically wrong routes may all be counted as success.

7. Generic fields create false confidence.

Some compiled operations require a generic field such as “answer.” A registry destination can satisfy that field even when it does not contain the requested procedure or fact.

SEVERITY 1 — COVERAGE AND FRESHNESS

8. Curated intelligence is narrow.

Only seven service snapshots and one calendar record provide current content-bearing deterministic shortcuts. Adjacent offices, dates, fees, forms, and procedures still depend on live or indexed evidence.

9. Twenty-five source groups have zero indexed chunks.

This includes official_calendar, registration, academic_standing, student employment, graduate assistantships, employment portals, advising, ID cards, counseling, accessibility, technology support, organizations, social profiles, events, news, maps, parking, safety, emergency status, library, and academic support.

Some of these have curated records or live routes, but the knowledge index cannot independently answer them.

10. Registered does not mean indexed.

The manifest contains many registered URLs with chunk_count=0. Runtime capability summaries can look broad because registration is counted separately from usable content.

11. Snapshot tolerance introduces a freshness tradeoff.

Service and calendar snapshots are currently accepted for up to seven days. This prevents midnight rollover failures, but it is unsafe for rapidly changing hours, closures, availability, emergencies, or deadlines unless the response clearly exposes the verification date.

12. Class Planner availability is stale.

The current Fall 2026 dataset was fetched on 2026-08-09. At the runtime snapshot, availability was marked stale with approximately 528,857 seconds of age. Section metadata may remain useful, but open-seat claims should not be treated as current.

SEVERITY 1 — LIVE RETRIEVAL

13. Provider configuration is mistaken for provider availability.

/health reports capabilities from flags and configured credentials. It does not perform a live provider probe. A provider can be configured but unreachable, quota-limited, blocked, slow, or returning irrelevant results.

14. The 3.5-second turn retrieval budget trades completeness for speed.

This prevents 30–40 second waits. It also means difficult live lists may return only verified portals or partial findings. “Any complexity at lightning speed” is impossible when the answer requires external networks and page parsing; the system must choose a documented latency/completeness policy.

15. Detached cancellation can leave cleanup work running.

The retrieval controller no longer waits for cancellation-resistant provider tasks. This protects response latency, but background cleanup and resource usage must be monitored under concurrency.

16. Page and provider diversity is uneven.

Some official sites use JavaScript, Cloudflare, authenticated portals, PDFs, or nonstandard HTML. The request-time fetcher intentionally does not use browser automation. Snippets and destination links may be the only evidence.

SEVERITY 1 — ARCHITECTURE

17. Core files are too large.

hybrid.py and ask.py combine too many responsibilities. Adding another special case can affect routing, budgets, citations, streaming, and fallback behavior in one file.

18. Legacy and current paths coexist.

Execution v2, legacy RCCS, non-RCCS, streaming, and non-streaming behavior remain in ask.py. Feature flags decide which path runs. Test coverage can accidentally validate a different path than the browser uses.

19. Multiple classifiers can disagree.

Legacy intent, RCCS classification, campus compiler, taxonomy match, conversation context, and task state all influence routing. There is no single typed authority or explicit conflict-resolution stage.

20. Full-spectrum vocabulary can overpower ordinary language.

The 50,000 planned-query corpus and taxonomy expand recall, but unusual phrase matches can inject a category that is lexically plausible and semantically wrong. More routing data is not automatically more intelligence.

SEVERITY 2 — PRODUCT BOUNDARIES

21. Class Planner does not register courses.

It can save selected sections locally and copy CRNs. It cannot write to Banner or reserve seats.

22. No personalized student truth.

No grades, holds, degree audit, account balance, financial-aid status, personal schedule, advisor assignment from an authenticated record, or registration eligibility.

23. Browser persistence is local-only.

Conversations and schedules can disappear when storage is cleared and do not follow the student across devices.

24. ACM Panel is not production-ready.

It is separate. Most modules are fixtures/scaffolds. Its existence must not be counted as AskMcNeese campus-assistant capability.

SEVERITY 2 — OPERATIONS, PRIVACY, AND OBSERVABILITY

25. Question text and debug traces are enabled locally.

ASKMCNEESE_LOG_QUESTION_TEXT=1 and ASKMCNEESE_DEBUG_TRACE=1 store full questions and large route traces. A production policy needs retention, access, redaction, deletion, and consent decisions.

26. Local stores are not production durability.

Guest and planner SQLite files require persistent disks and careful single-writer assumptions. Production design expects managed PostgreSQL for live planner and may use PostgreSQL for guest identity.

27. No broad live quality gate exists in CI.

CI runs unit tests and builds, but the four-question golden eval and 12-question capability set are not part of the CI workflow.

28. Documentation contains target/current contradictions.

Some architecture documents describe a common/ package, folderized web search, or integration-test structure that does not exist in the current tree. Developers can implement against an obsolete target if they do not verify current code.

SEVERITY 2 — TEST DESIGN

29. Most tests validate selected rules, fixtures, and mocks.

They are valuable regression protection but heavily favor already-known questions and branches.

30. There is no statistically meaningful unseen-query evaluation.

No balanced dataset currently measures domain accuracy, intent accuracy, entity extraction, required-field selection, evidence relevance, answer correctness, citation entailment, conversation continuity, and latency together.
