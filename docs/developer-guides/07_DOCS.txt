PRECEDENCE (WHAT TO TRUST)
================================================================================

When documents conflict, trust in this order:

1. The actual code (backend/, frontend/, etc.)
2. Tests (show what code should do)
3. developer-guides/ (this folder)
4. CURSOR_SYSTEM_TRUTH_AUDIT_2026-08-15/
5. Implementation records
6. Older docs

If documentation says one thing but code does another:
  → The code is correct
  → The documentation needs updating

================================================================================
DOCUMENTATION STANDARDS
================================================================================

PRINCIPLES:

1. ACCURACY OVER MARKETING
   - Don't claim capabilities we don't have
   - Be honest about limitations
   - "We attempt to..." not "We perfectly handle..."

2. CLARITY OVER BREVITY
   - Explain concepts fully
   - Use examples
   - Define technical terms

3. PLAIN LANGUAGE
   - Write for a "normal person" not just developers
   - Avoid unnecessary jargon
   - Explain what things DO, not just what they ARE

4. ATTRIBUTION
   - Always state: ACM project, not official McNeese
   - Don't imply institutional authority
   - Credit sources and ownership correctly

5. MAINTAINABILITY
   - Date documents
   - Note when things change
   - Link related documents
   - Use consistent structure

6. TRUTHFULNESS
   - Don't exaggerate
   - Admit what doesn't work well
   - Document known issues
   - Clarity ≠ false claims

================================================================================
WHAT NOT TO DOCUMENT
================================================================================

DON'T DOCUMENT:
  - Temporary experiments
  - Incomplete features (document when complete)
  - Internal implementation details that change frequently
  - Generated code (it's self-explanatory from source)
  - Obvious functionality (don't say "this function adds two numbers")

DO DOCUMENT:
  - Why something exists (not obvious from code)
  - How to use/configure/extend
  - Known limitations
  - Common issues and solutions
  - Non-obvious design decisions
